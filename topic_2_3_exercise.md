# Практическое упражнение: Спроектируй API Order Service для ShopWave

> **Тема:** 2.3 — API Design
> **Инструменты:** Swagger Editor (editor.swagger.io), шаблон `templates/api_spec_template.yaml`

---

## Контекст

Вы — системный аналитик ShopWave. Компания переходит с монолита на микросервисы. Ваша задача — спроектировать REST API для **Order Service** (сервис заказов), который будет использоваться витриной, мобильным приложением и другими сервисами.

---

## Задание

### Шаг 1. Спроектируйте ресурсы и URL (15 мин)

Даны бизнес-требования к Order Service. Для каждого требования предложите URL и HTTP-метод:

| # | Бизнес-требование |
|---|------------------|
| 1 | Создать новый заказ (клиент оформил покупку) |
| 2 | Получить заказ по ID (просмотр деталей заказа) |
| 3 | Получить список всех заказов с возможностью фильтрации по статусу и дате |
| 4 | Получить заказы конкретного клиента |
| 5 | Обновить статус заказа (например, «оплачен» → «в сборке») |
| 6 | Отменить заказ |

**Формат ответа:** таблица со столбцами «Метод», «URL», «Описание».

**Требования к URL:**
- Существительные, не глаголы
- Глубина вложенности ≤ 3
- Коллекции — множественное число
- Фильтрация и пагинация — query-параметры

---

### Шаг 2. Определите статус-коды и тела ответов (10 мин)

Для каждого из 6 эндпоинтов определите:

- Какой статус при успехе (200, 201, 204)
- Какие статусы при ошибках (400, 404, 409, 422)
- Что должно быть в теле ответа при успехе
- Что должно быть в теле ответа при ошибке

**Формат ответа:** таблица со столбцами «Эндпоинт», «Успех (статус)», «Тело успеха», «Ошибки (статусы)», «Тело ошибки».

**Требования к телу ошибки:**
- Единый формат: `{ "error": { "code": "...", "message": "..." } }`
- `code` — машиночитаемый (например, `ORDER_NOT_FOUND`)
- `message` — человекочитаемый (например, «Заказ с ID 12345 не найден»)

---

### Шаг 3. Напишите OpenAPI YAML (25 мин)

Используя шаблон `templates/api_spec_template.yaml`, напишите полную OpenAPI 3.0 спецификацию для Order Service.

**Что должно быть в спеке:**

1. **Шапка:** `openapi`, `info` (title, version, description), `servers`
2. **Эндпоинты (paths):** минимум 5 из 6 требований
3. **Параметры:** path-параметры (orderId), query-параметры (status, customerId, limit, offset)
4. **Тела запросов (requestBody):** для POST и PATCH
5. **Модели данных (components/schemas):**
   - `Order` (id, customerId, items, status, totalAmount, createdAt, updatedAt)
   - `OrderItem` (productId, name, quantity, price)
   - `OrderCreate` (customerId, items, shippingAddress)
   - `OrderStatusUpdate` (status)
   - `Error` (code, message)
6. **Примеры:** хотя бы 1 `example` для каждого эндпоинта
7. **Безопасность:** `securitySchemes` с Bearer JWT

**Проверка:** откройте ваш YAML в [editor.swagger.io](https://editor.swagger.io/). Если справа появился Swagger UI без ошибок — спецификация валидна.

## Подсказки

### Как проверить YAML
1. Откройте https://editor.swagger.io/
2. Вставьте ваш YAML в левую панель
3. Если справа появился Swagger UI без красных ошибок — спецификация валидна
4. Попробуйте выполнить GET-запрос прямо из Swagger UI (кнопка «Try it out»)

### Частые ошибки в YAML
- Отступы: должно быть ровно 2 пробела (не табы!)
- `$ref` указывает на существующий путь, например `#/components/schemas/Order`
- `required` — массив имён полей, например `required: [customerId, items]`
- `enum` — список строк в квадратных скобках

### Типичные ошибки новичков в API Design
- Глаголы в URL (`/api/createOrder`)
- 200 на всё («у нас всегда 200, а ошибки в теле»)
- Забыли про пагинацию для списков
- Используют PUT для частичного обновления (должен быть PATCH)
